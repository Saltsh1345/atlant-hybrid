`ЗАВЕРШЁН — ЗАМОРОЖЕН`

## Исходное состояние

- В проекте уже есть MediaPipe Pose, camera hooks, overlays, калибровка, антропометрия и body-scan API.
- Отдельного маршрута `/scan` нет.
- Требуется исследовать существующие формулы и переиспользовать их без рефакторинга.

## Результат read-only аудита

- Переиспользуем без правок: `useCameraDevice`, `usePoseTracker`, `PoseOverlay`, `SilhouetteGuide`, `CameraStatusOverlay`, `analyzePoseLive`, `analyzeScanFrame`, `pushBodyScanSample`, `estimateAnthropometrics`, `evaluateScanQuality`, `captureVideoFrameJpeg`.
- Текущий поток landmarks уже работает: камера → `tick()` → `NormalizedLandmark[33]` → анализ/сэмплы/кадры.
- Для автозахвата используем существующий критерий устойчивости: 12 успешных проверок с интервалом 120 мс.
- Отдельного `hyperlordosis` boolean в проекте нет; требуется новая осторожная эвристика в `src/lib/scan/**`, маркированная как оценка, а не диагноз.
- Существующая антропометрия не измеряет предплечье отдельно; Этап 2 добавит длину предплечья и бедра как отдельные сегменты.
- Координаты MediaPipe нормализованы, `z` является относительным depth proxy, а не расстоянием в метрах.
- Для фронтальной камеры overlay должен учитывать зеркальность; формулы сохраняют исходные landmark-координаты.

## План внутри этапа

1. Провести read-only аудит camera, pose, calibration и bio-модулей.
2. Зафиксировать точную схему данных скана и критерии устойчивой позы.
3. Создать `/scan` и UI двух ракурсов.
4. Подключить существующий MediaPipe pipeline.
5. Реализовать автоматическую фиксацию при устойчивом совпадении с рамкой.
6. Рассчитать безопасные оценочные показатели осанки и длины сегментов.
7. Сохранить результат в Zustand и Supabase с RLS.
8. Проверить lint, типы, камеру и адаптивность.
9. Синхронизировать паспорт и остановиться на приёмке.

## Ограничения

- MediaPipe и расчёт по 2D-камере дают оценку, а не медицинский диагноз.
- Пользователь решил 2026-07-19 вводить рост вручную перед сканированием; значение сохраняется в Supabase-профиль.
- Решение владельца 2026-07-20: рост вводится только при первой верификации. Повторный вход в `/scan` читает `profiles.height_cm`; при валидном значении (140–220 см) ввод пропускается, камера включается сразу. Другие части Этапа 2 не менялись.
- Разрешение камеры требует ручного согласия пользователя в браузере.
- `hyperlordosisLikely` — только вычислительный признак по стойке в профиль; его нельзя трактовать как диагноз.
- Если пользователь в свободной одежде, качество скана и измерения сегментов снижаются; это отражается в результате.
- По решению владельца от 2026-07-20 экран результата показывает неактивную кнопку «К ПЛАНУ · СКОРО»; переход появится только после реализации маршрута `/plan` в Этапе 3.

## Ручные действия владельца

1. В Supabase Dashboard откройте **SQL Editor** и примените `supabase/migrations/202607190002_stage_02_body_scans.sql`. Автоматически применить миграцию нельзя: в рабочем окружении отсутствует настроенный Supabase CLI/доступ к проекту.
2. В обычном Chrome или Edge откройте `http://localhost:3000/scan`, войдите через Google. Укажите рост только при первом сканировании; при сохранённом значении камера должна включиться сразу. Дайте браузеру разрешение на камеру и завершите фронтальный и профильный захват.
3. В Supabase Table Editor убедитесь, что создана запись `body_scans`, а в `profiles` обновились рост и данные последнего скана.

Проверка Supabase REST от 2026-07-20: endpoint `body_scans` отвечает HTTP 404. Это подтверждает, что миграция пока не применена; без неё Этап 2 нельзя принимать и замораживать.
